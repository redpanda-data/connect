# S3 sink benchmark results

> ## ⚠️ Metric validity notice — read before quoting any number below
>
> The sink sidecar's `total_files_size_bytes` counter, which every `mean/median MB/s`
> figure on this page derives from, had two defects fixed on 2026-09-23. Runs before that
> date are affected to differing degrees.
>
> **1. Pagination zeroing (all runs before 2026-09-23).** The counter came from
> `aws s3api list-objects-v2 --query "sum(Contents[].Size)"`. The AWS CLI applies `--query`
> **per page**, so once a prefix held more than 1000 objects the call returned one sum per
> page — a multi-token string — which a numeric guard rejected, setting the size to 0 for
> the remainder of the point. Signature: real values for the first ~24-42 samples, then
> **every later sample exactly 0.000** while `total_records` kept working. Effect:
> `mean_mb_s` understated by roughly 3x and `median_mb_s` forced to 0.00. Recover the true
> value from the non-zero samples in the run's JSON, or use the 2026-09-23 run.
>
> **2. Empty prefix reported as unknown (briefly, 2026-09-23).** A prefix with no objects
> yet made the CLI error, which was then treated as "size unknown" and omitted — and
> because `ParseIcebergSeries` drops a frame entirely when the bytes line is missing, whole
> frames were discarded including their records. This inflated a bursty engine's mean by
> dropping its genuinely-idle intervals. Fixed by querying `Contents[].Size`, so an empty
> prefix is a true zero.
>
> **Canonical live-stream result: the `orders-live — 2026-09-23` section at the bottom of
> this page.** It is the only live-stream run with both defects fixed, a correctly-sized
> load generator, and a verified full measurement window on every Connect point.
>
> **Known residual bias:** S3 `LIST` can return an incomplete page set while objects are
> being written, making the cumulative counter briefly decrease. `ParseIcebergSeries` skips
> the negative delta but counts the inflated recovery delta, overstating per-delta means by
> ~13% for **bursty** writers. Measured on 2026-09-23: Connect 0 non-monotonic steps (no
> bias); Kafka Connect 7 steps (+13.4%). Connect figures are unaffected.

### Validity and caveats for this run

**All three instrumentation defects that invalidated earlier live-stream runs are fixed
here, and each was verified on live infrastructure during the run**: the byte counter
incremented correctly past 1,175 objects across a genuine 2-page listing; the sidecar
emitted 47/47 frames where it previously emitted 1; and an empty prefix recorded a true
`0` rather than being dropped.

| engine | verdict |
|---|---|
| `connect`, all 4 points | **Valid.** Full measurement window (~1,480 s, 124-126 samples each). |
| `kafka_connect`, 1 and 2 vCPU | **Valid.** Full window (1,501-1,531 s, 116 samples each). |
| `kafka_connect`, 4 and 8 vCPU | **Not usable.** The worker stopped ~2 min and ~1 min into a 25-minute window (12 and 9 samples). The `mean MB/s` of 4.394 and 2.301 in the table above cover only those first minutes and must not be read as sustained throughput. |

**The `mean msg/s` column reads 0 for Kafka Connect, and the `Δ vs Connect` column
therefore reads `-100%`. That is an artifact, not a result.** `total_records` comes from
the engine's consumer-group offsets, and the Aiven S3 Sink connector did not commit any
during these runs — `CURRENT-OFFSET` was `-` on every partition while the connector was
demonstrably writing objects. Compare the engines on MB/s, not msg/s.

**Methodology changes made for this run, both deliberate:**

1. **Load generator raised to `c8g.4xlarge`** (`infra.load_gen.instance_type`). The default
   `c8g.large` has a *sustained* network allowance of 0.937 Gbps (117 MB/s) against this
   scenario's 360 MB/s target, so it delivered target only while EC2 burst credits lasted
   and was then shaped down — silently capping the producer at ~40% of target in every
   earlier live run. Verified fixed here: the producer held 98-100% of target throughout,
   with TCP send queues drained.
2. **Kafka Connect heap raised** (`matrix.go_mem_limit_per_vcpu` 8 → 20, giving 15/20/20/20
   GiB). At the previous 6 GiB the 1-vCPU worker died with 13 cascading
   `OutOfMemoryError`s ~7 minutes in, abandoning its consumer group while the REST API
   still reported `RUNNING`. This provisions *resource* rather than retuning behaviour: the
   flush interval determines the connector's object size and throughput profile, which is
   the quantity under measurement, so it was left unchanged.

**Interpretation.** Redpanda Connect's mean tracks its peak closely (31.29 vs 34.54 MB/s at
1 vCPU; 55.51 vs 60.48 at 8), the signature of a continuously-writing sink. Kafka Connect's
mean sits far below its peak (2.87 vs 41.33 at 1 vCPU; 5.05 vs 64.53 at 2), reflecting a
connector that buffers and flushes periodically rather than writing continuously. Where
both engines are valid the sustained ratio is 10.9x at 1 vCPU and 8.7x at 2 vCPU.

**Open item.** Kafka Connect's 4- and 8-vCPU live-stream points remain unmeasured. The
worker's own log was uploaded to the per-run results bucket, which is destroyed at
